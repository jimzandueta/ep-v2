PAIN POINTS

Where the current system
breaks down.

Eight structural issues across product, sales, and engineering, all rooted in the same design choices.
01
PRICING
Partner pricing is hidden in the URL
/enroll/:partnerKey silently controls pricebook selection and free-product behavior.
02
ROUTING
Partner-key link complexity
Route path, query params, subdomain, and environment config all shape the same page.
03
LIFECYCLE
No monthly pricing support
Frequency is product-specific; lifecycle logic is scattered across UI helpers.
04
SECURITY
Weak security posture
Permissive CORS, limited validation, no identity plane for authenticated routes.
05
ARCHITECTURE
One Lambda for everything
Products, coupons, orders, people, payments all route through RegalProducts.
06
STATE
No session or draft model
Refresh the page and progress is gone. No resume, no recovery.
07
TENANCY
No tenant model
Firm context is inferred from link params & payload, not enforced.
08
RELIABILITY
Payment & records coupled
Partial failures leave orphaned Salesforce records, no idempotency, no reconciliation.
01 · CURRENT STATE05 / 25
OPERATIONAL CONSEQUENCES

What these gaps mean in practice.

Mapping current pain points to legacy evidence and required changes.
PARTNER & PRICING
Adding a partner or price rule, code changes in multiple places.
Partner key drives URL routing, backend partner lookup, and pricebook branching; frontend helpers render price display.
EXTENSIBILITY
Adding products or journeys, more branching; not reusable.
Product-specific steps (employment, address, Credit Block, ChexSystems) are hard-coded rather than expressed as a platform rule set.
RECOVERY
Partial failures can leave orphaned or inconsistent records.
Order submission creates people and payment objects before hosted checkout completes; no idempotency or reconciliation model.
SELF-SERVE & BM
Returning-client and BM flows are not core platform features
Public flow is unauthenticated; there is no shared identity plane, no tenant model, and no portal APIs.

SECTION 3 · TECHNICAL10 / 25
KEY DECISIONS

Six platform decisions that guide the rebuild.

DECISION 01
Salesforce remains the system of record
Firms, clients, pricing rules, subscriptions, and BM ownership stay anchored in Salesforce. V2 reads from it, while V1 continues writing payment-adjacent records.
Trade-off: Slower reads, handled through caching.
DECISION 02
Blackthorn remains the payment path
Hosted PayLink keeps card data outside Regal infrastructure and preserves the proven payment flow.
 
Trade-off: Reuse the existing Java payment adapter.
DECISION 03
Keycloak becomes the identity layer
One identity layer supports consumer web, BM portal, admin, and mobile clients.
 
Trade-off: Tighter dependency on existing Keycloak.
DECISION 04
Pricing authority moves to the server
The server returns the approved product and price for each enrollment flow. V2 no longer accepts caller-supplied pricing.
Trade-off: Coupons remain checkout-time only.
DECISION 05
Tenancy is keyed by firm
 
Routing, storage, and audit behavior are separated by firm, without creating one realm or database per tenant.
 
Trade-off: Tenant rules are enforced in middleware, not infrastructure.
DECISION 06
Recovery is designed into the platform
Sessions, drafts, and payment attempts are tracked with retry-safe keys. Scheduled reconciliation repairs drift automatically.
Trade-off: More operational moving parts to manage.
03 · TECHNICAL11 / 25
SYSTEMS OF RECORD

Clear ownership across systems.

Authoritative business state stays in Salesforce and Blackthorn. Runtime state lives in DynamoDB. Identity and access stay in Keycloak.
Salesforce
AUTHORITATIVE · BUSINESS RECORDS
 
  • Firms, partners, clients
  • Pricing_Rule__c
  • Pricing_Exception__c
  • Subscription__c
  • Client_Manager__c
  • Product2 catalog
Blackthorn
AUTHORITATIVE · PAYMENT RECORDS
 
  • Sales Documents
  • Line Items
  • Transactions
  • Hosted PayLink sessions
  • Payment completion callbacks
Keycloak
AUTHORITATIVE · IDENTITY & ACCESS
  • Users & credentials
  • firm_id claim
  • sf_account / sf_contact
  • tenant_role
  • MFA policy
DynamoDB + S3
RUNTIME STATE · NON-AUTHORITATIVE
  • EnrollmentSession
  • EnrollmentDraft
  • Pricing cache
  • Idempotency keys
  • Deferred uploads (S3)
Rule: Runtime state can support the flow, but it cannot become the business record. If finance, ops, or the client depends on it, it belongs in Salesforce.

ARCHITECTURE · LAYER BY LAYER

Each layer has one job, and one reason to change.

Layer Responsibility Solves today’s pain of… Supports the mission by…
Client & Frontend
Next.js · ECS Fargate 		Render route families, SSR catalog, and hand off to hosted checkout Product-specific pages, inconsistent routing, wrong-price flashes Creating one coherent surface for every persona
Session & Draft
DynamoDB 		Store anonymous sessions, resumable drafts, and idempotency keys Lost progress, browser-only state, duplicate submissions Making enrollment resumable and safe to retry
API & Orchestration
API Gateway · Node services 		Validate session and tenant context, then coordinate submission Monolithic Java Lambda handling too many concerns Isolating services so changes are safer
Pricing & Eligibility
Node.js · Salesforce reads 		Resolve Product2 variant, price source, and availability state Browser-side pricing and product-specific flags Making pricing deterministic and auditable
Identity & Tenancy
Keycloak · middleware 		Enforce auth, firm_id claims, MFA, roles, and tenant boundaries Split identity behavior and link-inferred context Supporting self-serve and BM flows on one identity model
Payment & Recovery
v1 Java · Blackthorn · Step Functions 		Create PayLinks, handle callbacks, and reconcile post-payment writes Orphaned records, dropped callbacks, browser polling Treating reconciliation as platform behavior
